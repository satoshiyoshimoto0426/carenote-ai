## 0. 結論（先に3行）

1. **技術的には5工程すべて実装可能**。ただし③④は「AIが全自動で確定」ではなく「AIが下書き → 職員が押して確定」でのみ成立する（公開APIが無いため）。
2. **③（支援経過への転記）は、カイポケ公認の既製品が2026年3月から存在する**（エス・エム・エス×ウェルモ）。自作の前に、買うか・作るか・組み合わせるかの経営判断が要る。
3. **⑥（個人情報）は仮名化だけでは足りない**。要配慮個人情報の取得同意・AIベンダーの取扱い契約・医療情報GL第7.0版（介護事業者が明記された）への準拠・対応表の安全管理の4点が要件。

## 1. 工程ごとの可否（一次情報ベース）

| 工程 | 可否 | 方式 | 主な制約 |
|---|---|---|---|
| ① 電話を録音 | ○ | クラウドPBX（通話録音＋Webhook）／AIレコーダー端末 | 録音の告知義務は無いが**利用目的の公表義務はある** |
| ② AIが要約 | ○ | クラウドAI（仮名化前提）／端末内Whisper | 要配慮情報を含むため送信先の設計が要 |
| ③ 支援経過へ転記 | △ | **半自動入力のみ**（公開APIもCSVも無い） | 既製品が存在。規約はID第三者利用を禁止 |
| ④ アセスメントへ追記 | △ | 半自動＋**既存本文の読み取り→マージ** | 上書き事故＝記録消失の実害リスク |
| ⑤ Googleカレンダー登録 | ○ | Calendar API `events.insert` | 組織内限定なら審査不要・追加費用なし |
| ⑥ 個人情報の担保 | ○（設計次第） | 仮名化＋同意＋契約＋GL準拠の4層 | 「仮名化すれば個人情報でなくなる」は誤り |

## 2. ③ 支援経過への転記 ── 最重要の発見

### 2.1 公開APIは無い。実在する連携はすべてRPA

- カイポケの外部連携について、エス・エム・エスは公式リリースで**「RPAなど」による自動転記**と説明している（APIの語は無い）。
  出典: https://www.bm-sms.co.jp/news-press/prs_20260325_kaipoke-welmo/
- 訪問スケジュールSaaS「ZEST」との連携も、ベンダー公式が**「RPAによるデータ連携」**と明記。
  出典: https://zest.jp/corporate/news/20220407
- kaipoke.biz / ads / houkan / bm-sms.co.jp / policy.bm-sms.co.jp を確認した範囲で、開発者向けAPIドキュメント・パートナー制度の公表ページは**見つからなかった**（非公開の個別提携の存在は否定できない）。

### 2.2 公式CSVルートも使えない（第5表は対象外）

- カイポケのCSV入出力は**ケアプランデータ連携システム対応帳票に限定**され、対応表に「支援経過（第5表）」「アセスメント」の行は存在しない。
  出典: https://ads.kaipoke.biz/status-of-care-plan-data-linkage-system/
- 大元の**ケアプランデータ連携標準仕様 第4.1版（令和6年10月・厚労省老健局）**を全文（855行）検索した結果、「支援経過」「第5表」ともに**0件**。対象は利用者補足情報／第1〜3表／第6表／第7表。
- 国の**介護情報基盤**（令和8年4月から順次稼働・令和10年4月までに全市町村）の共有対象は被保険者証・要介護認定・福祉用具・住宅改修・ケアプラン・LIFEの一部で、**介護記録は入っていない**。
  出典: https://www.mhlw.go.jp/stf/newpage_59231.html
- ケアプランデータ連携システムは**2027年1月に介護WEBサービスへ統合**予定。

→ **結論：支援経過に外部から書き込む公的な口は、現時点で存在しない。**

### 2.3 カイポケ公認の既製品が既にある（2026年3月〜）

エス・エム・エスは2026年3月25日、ウェルモと戦略的パートナーシップを締結。副題は「AI要約とRPAの連携で介護現場の『ケアに向き合う時間』を創出」。

| 製品 | 機能 | 料金（公式LP） |
|---|---|---|
| ミルモレコーダー | 会話を録音→AIが文字起こし→**支援経過記録・サービス担当者会議録・モニタリング・課題分析標準項目・F-SOAIP・訪問看護記録書 等の様式に沿って要約** | ¥5,000/月（40時間/月）・無料トライアル3時間 |
| ミルモAI | 各種計画書作成・課題分析・FAX自動仕分け | LP に記載なし |
| ミルモオートメーション | **AIが要約したデータをカイポケへ自動転記**（設定はウェルモが代行） | 在宅 月額7,000円〜・施設 25,000円〜・初期40,000円〜 |

出典: https://lp.recorder.milmo.jp/ ／ https://lp.automation.milmo.jp/
注記：自動転記の活用可否は**入力箇所によって異なる**（公式脚注）。95%削減事例には効果を保証しない旨の注記あり。

### 2.4 規約上の線引き

- 共通規約：「会員は、**ID等を第三者に利用させる行為**、貸与、譲渡…をしてはならない」「本サービスの**目的外使用**をしないものとします」。
  「目的外使用」「なりすまし」は**無催告の利用停止・契約解除事由**。最終改訂 2026-02-25。
  出典: https://policy.bm-sms.co.jp/business/terms/sms_keiei_shien-SMS_keiei_shien_kyotsu
- 「スクレイピング」「RPA」「ボット」の語は規約に無い（2026-06 調査と同じ結論）。
- **設計上の含意**：事業所のIDを外部業者のサーバに渡して代理ログインする方式は「ID等を第三者に利用させる」に抵触しうる。
  一方、**職員が自分でログインした自分のPCの画面上で、職員がボタンを押して入力を補助する**方式（＝既存のブラウザ拡張）は、この条項の射程外と整理する余地がある。ただし最終判断はSMS社。照会文面は [KAIPOKE-SMS-INQUIRY.md](KAIPOKE-SMS-INQUIRY.md) に作成済（未送付）。
- 免責条項：SMS社の賠償上限は**直近6ヶ月の対価総額**。1ヶ月前告知で機能の変更・中止が可能 → **画面依存の方式は壊れる前提で作る**。

### 2.5 自社の既存資産（実装済み）

`extension/src/adapters/kaipoke.js` に第5表（支援経過）の流し込みが実装済み。

## 3. ④ アセスメントへの「追記」── 最も危険な工程

- カイポケのアセスメント欄は既にDOM取得済（主訴・生活歴・全体まとめ等のtextarea）。
- **しかし現在のアダプタは上書き**：`writeField()` はネイティブ value セッターで代入するため、**既存の本文は消える**。
  該当: `extension/src/adapters/kaipoke.js` の `writeField()`
- 「該当部分に追記」を実現するには「既存本文を読む → AIが差分をマージ → 書き戻す」が必要で、失敗した場合の実害は**過去の記録の消失**。
- 設計上の必須要件（案）：
  1. 書き込み前に既存本文をスナップショットしてCareNote AI側に退避（元に戻せるようにする）
  2. 追記は**末尾に日付つきで足す**方式に限定し、本文の書き換えはAIにさせない
  3. 差分は画面上でビフォー・アフター表示し、職員が承認してから書き込む
  4. 「AIが状態像の変化を検知した」は**提案までにとどめ**、どの項目に足すかの判断は人

## 4. ⑤ Googleカレンダー ── 技術的に最も容易

- `events.insert` でイベント登録可能。標準利用は**追加費用なし**（毎分1万/プロジェクト・600/ユーザー・1日100万件が課金しきい値）。
- Calendar は Google が **sensitive スコープ**の例に挙げており、一般公開アプリは審査（通常3〜5営業日）が必要。
  **自社 Workspace / Cloud Identity 組織内限定なら審査不要**。
- サービスアカウントによる代理登録は**ドメイン全体の委任**＝Workspace 管理者設定が前提。
- 注意：予定のタイトルに利用者名を入れると、カレンダーが個人情報の保管先になる。**記号（A様）＋用件のみ**にする設計が要る。

## 5. ⑥ 個人情報の担保 ── 4層で組む

### 5.1 通話録音そのもの

- 個情委Q&A **Q1-10**：「通話内容から特定の個人を識別することが可能な場合には個人情報に該当します」「個人情報取扱事業者は…**録音していることについて伝える義務までは負いません**」。
  ただし**利用目的の通知・公表義務は負う**（法21条）。
- 個情委Q&A **Q1-11**：識別できない録音記録は「基本的には個人情報に該当しません」が、容易照合性があれば該当しうる。
- 総務省FAQ：通信の秘密の侵害は「**通信当事者以外の第三者**」による知得等。当事者端末に保存された通話録音は「電気通信事業者の取扱中」に当たらない。ただし**有効な同意なき取得・利用・提供には不法行為責任が生じ得る**と留保。
- 厚労省カスハラ指針は「顧客等とのやり取りを録音・録画すること」を対処例に挙げ、**対策は令和8年10月1日から義務化**。

→ 実務判断：法律上「録音します」の告知義務は無いが、**利用目的の公表は必須**であり、事業所の信頼を考えれば冒頭アナウンスを入れる方が安全。

### 5.2 要配慮個人情報

- 障害（身体・知的・精神〔発達障害を含む〕）は施行令2条1号・規則5条、病歴は法2条3項本文。
- **取得に原則あらかじめ本人同意**（法20条2項）。オプトアウトによる第三者提供は不可（法27条2項ただし書）。
- 漏えいは**1件でも**委員会報告と本人通知の対象。
- 介護分野では掲示による黙示の同意ではなく、**利用開始時の文書同意**が求められる。

### 5.3 クラウド・AIベンダーの位置づけ

- 個情委Q&A **Q7-53**：判断基準は「保存している電子データに個人データが含まれているかどうかではなく、**クラウドサービスを提供する事業者において個人データを取り扱うこととなっているのかどうか**」。取り扱わないなら提供にも委託にも当たらない。
- **Q7-54**：提供に該当しない整理でも、**利用する事業者自身の安全管理措置義務は残る**。
- **注意**：個情委は令和6年の注意喚起で、規約上の監視・分析権限や保守用IDの存在等を理由にベンダーを個人情報取扱事業者と認定した実例を示している。**この整理は崩れやすい**。
- 海外：十分性認定は**EUと英国のみ**、米国は「外国」。ベンダーが取り扱うなら法28条の同意＋規則17条2項の3項目の情報提供。取り扱わない整理でも「**外的環境の把握**」として、ベンダー所在国名とサーバ所在国名を明らかにし措置内容を本人の知り得る状態に置く必要がある（Q10-25）。
- 自社の既存整理：Anthropic の DPA は署名不要で既に有効・30日自動削除・学習不使用（[LEGAL-DPA-INQUIRY.md](LEGAL-DPA-INQUIRY.md)）。ZDR は $100K+ コミット条件で見送り済。

### 5.4 仮名化の限界（重要）

- 個情委FAQ：「仮名加工情報を作成した個人情報取扱事業者においては…**原則として『個人情報』（法第2条第1項）に該当する**」。
  → **「氏名をA様に置き換えたから個人情報ではなくなる」は成り立たない。**
- 対応表（実名⇔記号）は「**削除情報等**」であり、法41条2項・規則32条の安全管理措置の対象：
  ①取り扱う者の権限・責任の明確化 ②規程類の整備と取扱状況の評価・改善 ③正当な権限を有しない者による取扱いの防止。
- 加工基準は規則31条（識別記述等の削除・個人識別符号の削除・財産的被害のおそれのある記述の削除）。
- 日本語のPII自動検出：GiNZA/spaCy 日本語モデル（NER搭載・MIT）＋ Presidio が現実解。ただし **Presidio に日本固有の recognizer は同梱されず自作が要る**（公式は既定で英語のみ）。
- 自社の既存実装：`lib/privacy/pseudonymize.ts`（maskNames/restoreNames/expandAliasVariants）＋ `crypto.ts`（AES-256-GCM）。
  **既知の穴**：置換できるのは**登録済み利用者の氏名のみ**。電話で出てくる家族名・他事業所の担当者名・施設名は置換されない。

### 5.5 準拠すべき公的基準

- **医療情報システムの安全管理に関するガイドライン 第7.0版（令和8年6月）── 適用対象に「介護事業者」が明記**。
  - 第14章：**二要素認証**
  - 第17章：**アクセスログ**の要件
- 電子カルテ情報共有サービスは医療機関・薬局向けで、介護記録は対象外。

## 6. 選択肢（経営判断）

| 案 | 内容 | 利点 | 欠点 |
