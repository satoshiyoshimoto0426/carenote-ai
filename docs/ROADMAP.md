## 3. フェーズ一覧（依存順・並行レーン明記）

### 【最優先・実装】P-PRIVACY-ORG｜事業所内で使ったときに黒塗りが成立するか ★G3b

> 検品（2026-09-12）で判明。名簿の読み出しは `lib/db/clients.ts` の `loadAliases` が3つの表すべてを
> `created_by = ログイン職員` で絞っており、`org_id` は書き込むだけで読み出しに使っていない
> （`supabase/clients_documents.sql` のコメント「org共有はフェーズ2」）。
> つまり**職員Bが、職員Aの登録した利用者の実名をメモに書くと、記号に置き換わらないまま AI へ出る**
> （型置換と漏れ検査は職員Bの名簿で行われるため止まらない）。1社＝複数職員の運用では必ず踏む。

**吉本さん決定（2026-09-12）: (A) 事業所で共有する。**

- ✅ 実装（2026-09-12）: `lib/db/clients.ts` に `scopeExpr` を新設し、利用者・実名・関係者の3表すべてを
  「事業所の行 ＋ 組織に入る前の自分の行」で読む。
  組織に所属していなければ従来どおり本人のみ（`org_id` が null 同士を同じ事業所とみなさない＝他テナントと混ざらない）。
- ✅ 独立審査（2026-09-12）の critical を反映:
  - **記号（A様）の採番を「件数」から「範囲内の最大＋1」へ** ── 件数だと、事業所の行と
    「組織に入る前の自分の行」が混ざったとき同じ番号を二度引き、別人が同じ A様 になる
    （黒塗りを戻すと**他人の氏名**が帳票に入る）。競合時は1回だけ取り直す。
  - **安全網 `assertCodesUnique`** ── 名簿を作った結果、同じ記号に違う氏名があれば送信を止める。
    移行の適用有無に依存せず「記号は一意」を機械で守る。
  - **名簿の件数上限（900件）で fail-closed** ── PostgREST は既定 1000 行で黙って打ち切る。
    欠けた名簿で黒塗りすると載らなかった人の実名が素通りするため、上限に達したら止める。
  - **壊れた `orgId` は例外で止める**（黙って「所属なし」に落とすと同僚の登録が名簿から抜ける）。
  - **実名の保存に失敗したら利用者ごと取り消す**（名前の無い利用者＝黒塗りされない利用者を残さない）。
  - `getRelatedPeople` は**親の利用者が範囲内か**も確かめる。未使用だった `getClientName` は削除。
- ✅ テスト: `lib/db/clients.test.ts` 23件（読み出し4本＋3表すべてに絞り込みが付く・採番・安全網・
  上限・ロールバック）、`lib/privacy/pseudonymize.test.ts`（記号⇄番号の往復 800件）
- ❗ **これだけでは有効にならない。吉本さんの作業が3つ要る**:
  1. ~~**Supabase で SQL を2本実行**~~ ✅ **2026-09-14 実行済**（吉本さん）── `supabase/client_related.sql` と
     `supabase/client_org_scope.sql`【手順1】（事業所ぶんの記号の一意制約）
  2. **Clerk で組織（Organizations）を有効にし、職員を1つの組織に所属させる** ──
     本番データの `org_id` は全件 null。組織に入るまで共有は始まらない。
     Clerk が `orgId` を返すのは「Active Organization（いま選んでいる組織）」がある時だけなので、
     **所属させただけでは null のまま**。各職員が画面で事業所を選ぶ必要がある
     （切替UIと状態表示は `components/SharingStatus.tsx` で 2026-09-14 に追加済）
  3. **既存データの移行（backfill）** ── 組織を有効にする前に登録済みの利用者は `org_id` が null で、
     **登録した本人にしか見えない**。`supabase/client_org_scope.sql`【手順2→3→4】を実行して
     事業所ぶんへ移す。手順2（記号の重複チェック）が0件でなければ手順3へ進まないこと
- 📊 本番の実測（2026-09-13・実名は読まずに件数と列だけ確認）:
  `clients` 2件（記号 A・B・**重複なし**／`org_id` は2件とも null）、`documents` 5件、
  `client_related_identities` は **2026-09-14 に作成済（HTTP 200）**＝503 は解消。
  記号に重複が無いので、移行（手順3）は安全に通る見込み。
- 🔜 有効化後の確認: 職員2アカウントで「Bのメモに A が登録した利用者名を書く → 記号に変わる」ことを実機で見る
- 📄 マニュアル（第①章の例外④・第②章の注意とFAQ）と DATA-HANDLING §3/§9 は
  「①組織の設定 ②既存データの移行 ③各職員が画面で事業所を選ぶ の3つが前提」に更新済。
  手順の正本は `docs/ADMIN-SETUP.md`

## 6. 最重要リスク（2026-09-12 時点）

1. **R-LEGAL**（最大）: 録音の文字起こし事業者（Genspark 個人プラン）に DPA が無く、同社規約が機微情報を想定していない。専門家レビュー次第で**録音経路を差し替える**（スマホ録音 → CareNote → OpenAI。実装済み・切替可能）
2. **R-KAIPOKE**: 規約NG／実機NGなら転記がコピペへ縮退（2条件KPIで価値を担保）
3. **R-FIELD**: 第1・2（送信の完了まで）・4・5・6段と拡張が**実機未確認**（第2段は確認画面の表示のみ・第3段は API 疎通 HTTP 200 まで）。残りの証拠はテストとビルド ── 実機8項目が最短の解消手段
4. **R-RETENTION**: 保持期限後の自動削除が未実装（説明書で「開発中」と正直に開示中）。手動対応の運用が回るか
5. **R-KNOWLEDGE**: 知見エンジンの律速は吉本さんの言語化時間（テンプレと反映運用の固定で軽減）
6. **R-RESPONSIBILITY**: 「AIが制度準拠を判断」は保証できない → 承認データモデル＋訴求限定＋人間の最終確認で設計として担保
7. **R-ORG**（新規・2026-09-12 検品で判明）: 黒塗りが**登録した職員のアカウント内でしか効かない**。複数職員で使うと、他人が登録した利用者の実名がそのまま AI へ出る → G3b で潰すか、運用で回避したうえで規程とマニュアルに明記する（マニュアルと説明書には反映済）
